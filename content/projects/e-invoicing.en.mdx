## Context

In Costa Rica every invoice is an electronic document: it is signed, sent to the Ministry of Finance (Hacienda) and accepted or rejected. During my internship at Argana I worked on a platform that does this for many companies at once, through a web app and an API for other systems, in the weeks before its launch.

My job was to make sure it would hold up. First, in the situations real businesses run into: concurrent requests, foreign currencies, invoices that have to be voided, and a tax authority that does not always answer. Second, with many companies sharing one database, each seeing all of its own data and nothing from anyone else.

## What I did

- **Wrote the full-repository audit and fixed all 17 findings**: 8 tax-compliance defects and 9 business-logic bugs.
- **Fixed row-level security policies that locked each company out of its own data**, and proved tenant isolation on all 20 tables with tests that run in CI.
- **Made invoice creation idempotent**: a retried request never issues the same invoice twice.
- **Hardened accounts, file uploads and outbound requests**, so a company can no longer be left without an administrator and uploaded files are checked by what they really contain.
- **Left the platform ready for the next person**: a repository that builds and runs from a fresh checkout with demo data, and no known high or critical vulnerabilities by the end of my internship.

## Result

- The platform was **ready to launch with no known open tax-compliance defects**.
- No known high or critical security findings or dependency vulnerabilities by the end of my internship.

## What I took from it

An audit is only as good as what closes it. Each finding ended with a fix and a test that would fail if the problem came back, so the next person does not have to trust my report: they can run it.

## Technical decisions

### Invoice numbers from an atomic counter

Each invoice needs a consecutive number per company, branch, terminal and document type, with no gaps and no duplicates. Counting the existing invoices and adding one breaks as soon as two requests arrive at the same time: both see the same count.

The number comes from a counter row that is locked and incremented atomically, **inside the same transaction that creates the invoice**. If the invoice fails, the transaction rolls back and the number is not used up. I moved every invoice number onto this counter, which removed any chance of a duplicate number reaching the tax authority.

### When the tax authority does not answer

Each invoice moves through explicit states, from signing to the tax authority’s final answer. If the tax authority times out, the platform does not send the invoice again; it **asks for the status** of the document by its key, with retries and backoff. I built those retries and the status query, plus a recovery job for invoices that would otherwise stay pending when no answer ever comes. And if the connection drops while an invoice is being issued, retrying returns the same invoice instead of a new number.

### Tenant isolation in the database

Isolation does not depend on every query remembering a `WHERE company_id = …`. The company is set on the PostgreSQL session with `SET LOCAL` inside each transaction, so it never leaks to the next request that reuses the pooled connection, and the tables use `FORCE ROW LEVEL SECURITY`, so not even the table owner skips the policies. I wrote the CI test that checks every table in both directions: each company sees all of its data and none of anyone else’s.

### Other changes

- **Idempotency:** a fingerprint per request means a retried call gets the original invoice back.
- **Accounts:** role changes can no longer leave a company without an administrator; new users need a confirmed email and join by invitation link instead of a shared password.
- **Uploads:** files are checked by their content signature, not by the type they claim to be.
- **API and webhooks:** pagination on every collection, more useful events, and end-to-end tests for API keys.
- **Subscription payments by bank transfer (SINPE):** the customer uploads the transfer receipt and the platform’s staff review it from a back office.
- **A clean start:** demo data with one account per role, and the end-to-end conformance gate really runs in CI.
