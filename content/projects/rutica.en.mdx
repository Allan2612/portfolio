## Context

Rutica is a mobile app for discovering what is nearby in Costa Rica: businesses, attractions, events and promotions, on a map, with reviews and favorites. People publish their own businesses, attractions and events, business owners post promotions, and premium plans give owners more room.

I built it with another student as a course project. Months later, before putting it in production, it needed a hard look: an app where anyone can publish content, rate others and pay for a plan has to hold up when someone does not use it the way it was meant to be used. I did that audit on my own, fixed what it found and took the app to production.

## What I did

- **Audited the whole repository:** 8 reports with more than 140 findings, from the database and security to UX, performance and legal compliance.
- **Turned the audit into a plan of 88 tasks in 8 phases** and carried it out, logging the 13 new problems that appeared along the way.
- **Moved the rules that protect the app into the database**, so nobody can skip them by talking to the database directly.
- **Covered the legal basics:** explicit consent at sign-up, a privacy policy draft under Costa Rica’s data protection law, and account deletion from inside the app.
- **Took it to production safely:** CI on every push, the database migration rehearsed on a copy of production, and a documented release order.

## Result

- **Rutica is in production**, with CI, preview deployments for `develop` and every pull request, and a documented release order.
- 87 of the plan’s 88 tasks are done. The last one is partial: loose `any` types went from 617 to 455, with a cap in CI so the number cannot grow back. A few legal details (tax, refunds, minimum age) are drafted and marked for a lawyer to confirm.

## What I took from it

Auditing code I helped write was humbling. The most serious problems were not in the screens I remembered but in what the database allowed when nobody went through the app. Since then I put the rules that protect people’s data where they cannot be skipped, and I write the test that proves they hold.

### Security rules where they cannot be skipped

A rule that only lives in the app can be skipped by anyone who talks to the database API directly. So the rules that matter are checked by the database itself, with PostgreSQL triggers and row-level security: who can approve a subscription, which role a new account gets, what happens when approved content is edited, and how much an owner can publish. A test applies the migration to an in-memory PostgreSQL (PGlite) and checks 28 of those rules on every push; if one stops holding, CI fails.

### One migration, safe to run twice

All the model changes live in one script. It is idempotent, so running it a second time changes nothing, and it runs inside a transaction, so a failure leaves the database as it was. That made it possible to rehearse it on a copy of production and then apply the same file with confidence.

### Other changes

- **Client-side security:** user content shown inside maps is escaped, links are validated before they are opened or saved, every admin route is protected, and the email functions require a session.
- **Performance:** a global cache policy for queries, reviews loaded on demand, and counts from aggregated queries.
- **Bugs:** a crash in the premium dashboard and sessions that were not kept whole.
- **Branches:** `main` and `develop` on Vercel, merged by pull request with CI green.
